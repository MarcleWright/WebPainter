# B · 从图片节点进入 AI 编辑或画板

[父任务](2026-11-18_01_drawing-board-workflow-and-open-performance.md) · [执行台账](2026-11-18_01_execution-loop.md)

## 范围

Image node 工具栏的「继续编辑」改为「AI 编辑」并采用魔法棒，保留其既有编辑逻辑。新增「画板中编辑」，同项目可读原图按方向校正后的像素尺寸生成 RGB8 画板，源图作为首个正式像素图层，投影确认后直接打开。沿用 A 的原 Canvas ticket、稳定 ID、重试及打开控制。空白画板创建和已有画板打开不受影响。

## 设计合同

1. ADA 客户端从 ready Image 原始表示拿来源 ID 和当前正式内容 hash，提供给有限创建合同。服务端以工作区内 Primary 为准，先以 trusted descriptor 验证 ready、角色、MIME 和声明大小，再通过存储 owner 的规范路径读取最多 50 MiB，读取时验证实际长度及 SHA-256，头部验像素和方向后方可解码。延用现有绘图资源的 PNG、JPEG、WebP 和 50 MiB 上限，拒绝多帧。PNG 需有界扫描 acTL 以识别 APNG，不能只依赖 Sharp 的 pages。工作区或源 revision 与原意图冲突时明确失败。
2. 使用 ADA API 已有 Sharp 读取，应用 EXIF 方向并转换到约定 sRGB RGBA8，固定 uchar 原始输出，校验方向后的宽高、4 通道与字节长度，保留非预乘透明度。WP main 扩展纯 codec 入口，用受限 RGBA8 构建图块和第一个像素图层，可在首层写历史 importedFrom。服务端创建记录权威保存来源身份。复制图层无原图保留义务，不能写入用于活跃依赖的 custom.source。源图删除后用户仍可编辑、保存和生成恢复候选。继续由原 native v1 编解码器校验，不引入复写格式。通过正式 embedded 包消费该能力。
3. 让同一个创建事务发布含图的 revision 1 与原请求回执。保留空白创建合同及旧 fingerprint，图片创建以规范化 title、源 artifact ID、Primary payload ID、revision 和 hash 生成独立指纹。读取资源前及事务内各匹配一次创建记录，已提交的真实重放与 removed／冲突结果不能依赖仍能读取源图。首次创建在写入时重核 Primary 身份，覆盖并发更新及删除。只对新建执行昂贵解码，不把它放进长时间数据库锁中。新建图片画板先通过进程内一个重载操作槽，覆盖读取、解码、编码、提交和应答，满时提示稍后重试，所有结果释放槽。4K 与候选尺寸上限记录 API 进程 RSS 与事件循环停顿。根据明确证据选安全上限，超限显式提示，尺寸不缩放。
4. 失败入口依 A 复用原 artifact/投影创建意图。源图来源是不可变 provenance。源项目检查及源身份和数据库内同一版本写入由服务端保证。源或投影失败时不得在新项目打开空画板。

## 容量审查后的调整

隔离 API 子进程以实际 HTTP 输入测得 4096² 和 8192 × 2048 的单张图片创建阻塞事件循环约 2.19 秒和 2.55 秒。单槽资源准入能控制内存并发，但其他请求仍会一起等待。因此保留 4096² 总像素／8192 单轴的阶段候选，先把同步 RGBA8 编码及 native inspect 放到该单槽内的 Node Worker，容量复验后再定。

- 服务端先按原固定包 manifest 及模块 hash 校验，Worker 只能 import 该验证后的 codec 数据 URL，使用静态 Worker 入口。Worker 不拥有项目权限、路径或数据库写入。输入传入独占 RGBA ArrayBuffer 和有限参数，输出用 transferable 归还 native 字节及 summary。TS 开发、打包 API 和 Cloud API 走同一入口。
- Worker 失败、退出、超时或无效输出时终止并等待资源收回，释放原重载槽且不进入写入。正式发布仍由原服务端事务和源身份终检完成。重复或异常消息只能确认同一 worker 所属请求。
- 使用相同 4K 和宽图复测端到端耗时、真实进程 RSS、事件循环最大停顿及并发轻量请求。固定峰值若仍由文件发布路径主导，再按测量处理对应 I/O，保持原 crash/replay 语义。选择是否保留满 4K 的依据须记录在评审结果。

Worker 对照样本将 4096² 图片导入的 API 进程最大事件循环停顿从约 2.28 秒降到 0.97 秒。轻量真实请求在 Worker 编码期间能处理，但发布有一笔约 0.94 秒的尾部响应。文件归属事务约 0.77 秒，另有正式响应读取约 0.18 秒。继续收敛新图片导入的候选文件写入：

- 沿用现有项目锁、事务、journal、候选路径、排他创建、操作 ID、回滚与崩溃清理，给 B 的图片创建选用同一文件 owner 的异步写入、flush、close 和回读校验。用有界分块读取验证实际长度和内容 hash。不可因为路径已存在或写入成功就略去 flush 或回读。
- 仍在原锁归属下完成校验和 pointer commit。保留正式发布前的候选安全性、测试 checkpoint 顺序及失败清退。旧空白创建与其他保存／恢复调用仍使用原路径，除非独立验证证明可无差异收敛。重复原意图不运行新解码。
- 复跑隔离容量场景，并发 probe 和 crash/replay 测试。服务端实际最长停顿与峰值由同一进程采样。若主要剩余在原响应完整读取，记录后续 D 对照，不以源码判断提速已达标。

## 最小验收

- 真实工具栏两个入口各自调用正确链路，禁用无可读源输入，AI 编辑无模型支出。
- 非方形透明 PNG、方向 6 的 JPEG、WebP，以及 APNG、动画 WebP、跨项目、格式或尺寸超限、源已改、并发双击、响应丢失后同请求重放。检查含图首版的层像素、大小、alpha 和 provenance，以及 artifact 重开。
- SQLite 和 PostgreSQL 核对同 ID 同输入重放、换源/换版本冲突、已提交后源删除仍可查原回执，已删除源后的打开、编辑、保存、恢复，以及提交失败时不留 ready 空板。复用独立 API 进程容量和崩溃检验。至少测 4K、候选上限以及并发槽超载。

## B 实现结果与独立复审

WP codec 定向 35/35 和类型通过，独立 Native 26/26。通用 WP main 5a3d670，embedded 7a37c44，固定包 8d810c07…f222。ADA 画板分支本地提交 395baa05。

前端真实 Chrome 通过普通拖入透明 PNG 与带 EXIF 方向 JPEG，通过新增工具栏按钮准确导入像素。173 × 91 与方向校正后 71 × 131 均有单张正式首层、对应 RGBA SHA 和同 ID 重开。双击只提交一份原请求及投影，原图节点不变。AI 编辑沿用原入口且本轮无需调用模型。B-I1 已完成同 ID 不确定结果随后权威 410 的回归，独立 Approved。

服务端合并后 PNG/JPEG/WebP、格式和尺寸边界、授权、来源变化、同长度损坏、三个真实崩溃点及旧记录重放经 SQLite/PG 定向核对。阶段 B 新用例 8/8，旧画板创建/保存/恢复四个选中组 4/4、API 与共享契约类型通过。另有 minified Node22 API 实际 HTTP 201 与精确 native SHA 证据，未经过正式 ASAR。独立对最终 e5b59f90…b674f 及新文件确认 Approved。B-I2 经两次设计复审改用专用 Worker 编码，初始候选文件走原 journal/锁／事务内的异步写和校验。
