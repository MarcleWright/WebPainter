# 4K 性能优化的产品方向

状态: 产品目标待验证, 原型主线已确定, 未实施、未承诺性能收益。技术证据与工期估算归 [4K 评估](../engineering/4K_SELECTION_ASSESSMENT.md)。

## 设计师实际遇到的问题

设计师选择车轮、车窗或车身局部后, 需要边拖边比较位置和比例。若内容明显落后于指针、不同区域分块跟进, 用户就难以判断当前效果, 会停下来等结果, 打断设计节奏。

性能优化要恢复这个试错过程, 不以更换语言、调整块尺寸或某个跑分提高作为产品完成标准。

## 四个方向

| 方向 | 用户感受到的变化 | 验收应关注什么 |
| --- | --- | --- |
| 跟手 | 选中内容随指针连续移动, 便于来回对比 | 首次提取延迟、拖动响应延迟、帧间隔尾部, 不只看平均 FPS |
| 画面连贯 | 当前画面表现同一个移动状态 | 是否持续出现不同块显示不同位置, 松手前后是否闪回 |
| 结果可信 | 预览和松手结果一致 | 透明度、蒙版、混合模式、上方调整层、颜色和选区边缘 |
| 操作稳定 | 原来的鼠标与撤销习惯保持 | 直接拖动无需额外确认按钮, 取消能恢复, 一次拖动一次撤销 |

拖动期间显示实时预览, 松手后固化结果。这里的区分是显示计算与正式数据写入的分工, 不是让用户松手后才看到变化。交互细节见 [约定](../design/INTERACTION_RULES.md)。

## 已确定的验证安排

1. 先执行未来获授权的 [原型任务 02](../ai/tasks/2026-11-05_02_4k-selection-preview-prototype.md): 主线为浮动选区状态 + 稳定资源 WebGPU 图层内实时合成, 松手正式写入。
2. 核心优化不缩减。原型验证限定 3840 x 2160 RGB 8 位、中/大选区和固定缩放前后对照, 一个 mask/opacity/Multiply/Curves 组合, 加一个小型透明边缘 fixture 验证像素和历史; 不展开完整排列或建立通用采集设施。
3. 原型通过后, 再定义 16 位及复杂剪贴、嵌套组和样式的完整覆盖, 并补齐拖动与保存/导出/自动保存并发一致性。原型是隔离实验入口, 未支持场景保留原路径, 不能从原型结果推导日常编辑全部可用。
4. 之后才评估 ADA 接入。当前只授权文档与任务规划, 不开始实现或排期。

主线选定见 [ADR-0002](../ai/decisions/ADR-0002_floating-selection-webgpu-prototype.md)。验证关口用于评估该主线在有限范围的可行性和扩展成本, 不用于做到一半才选择整体路线。

## 候选目标, 待真实样例确认

- 常见 4K 场景先以拖动稳定达到 30fps 以上且持续反馈为第一阶段目标, 60fps 为进一步目标。固定记录显卡、渲染后端、缩放和选区面积。
- 同时记录 P50/P95 帧间隔、首次提取耗时、输入到显示延迟以及松手到结果稳定耗时。不能用处理函数耗时换算正式 FPS。
- 性能提升不能靠悄悄取消蒙版、略过调整层或改变最终分辨率。若存在预览精度折中, 需明确范围, 并验证最终结果。
- 极端文档的降级行为另行设计; 不把 PhotoCraft 的仅轮廓降级直接作为常见 4K 场景的合格结果。

上述为产品层总体目标。按当前预期约百名用户和有限原型投入, 任务 02 的通过条件聚焦核心路径实际跑通、结果/操作正确及实窗明显改善; 30fps 为参考目标, 没有可信统计就明确写未测得, 不宣称达标。完整尾延迟、精细 GPU 像素读回、故障注入和资源审计在正式化时再定, 不叠加为本原型硬门槛。

## PhotoCraft 的产品启示

值得学习的是让交互反馈与最终写入分工、复用已有内容、把昂贵工作限制在变化区域, 并在压力过大时保持可理解的行为。两条预览路径、原生/Web 差别和不能照搬的历史语义, 见 [源码对照](../architecture/PHOTOCRAFT_REFERENCE.md)。目前没有两项目同条件人工拖动或生产构建 FPS 对比, 不以 Rust 语言本身推导体验上限。
